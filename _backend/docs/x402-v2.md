# x402 v2 encrypted inference

`POST /v2/inference` implements the official x402 v2 HTTP transport for the **exact EVM / EIP-3009 / EOA** payment path. Compatibility is tested with the published `@x402/core` and `@x402/evm` SDKs, version **2.26.0**, through real Postgres and disposable Anvil contracts. This is a supported subset: Permit2, ERC-1271 smart wallets, ERC-6492 counterfactual accounts, arbitrary facilitator APIs and other payment schemes are not implemented.

The existing `/v1` payment endpoints retain their custom protocol. Their payment tokens and `ReceiveWithAuthorization` signatures cannot substitute for a v2 `TransferWithAuthorization` signature.

## Deployment requirements

- Set `PAYMENT_MODE=authorized`, the actual `ARC_CHAIN_ID`, `USDC_ADDRESS`, `USAGE_METER_ADDRESS`, and the token's exact `USDC_EIP712_NAME` / `USDC_EIP712_VERSION`.
- Deploy the matching `UsageMeter` implementation, whose `X402_VERSION()` returns `2`. The API checks this capability before advertising a challenge. An older development deployment returns `503 X402_UNAVAILABLE`; no existing `.env`, chain or database is automatically reset or replaced.
- Configure the normal meter integrations, owner relay, durable signer journal and confirmation policy. Payers supply their own funded EOA; this path never mints tokens or borrows the relay's USDC. Gas is paid by the relay.
- API-key authentication, attested sessions, encrypted request bodies, model approval and agent mandates still apply. An external payer using an agent must open that agent's onchain mandate from its own wallet.
- Use the externally reachable URL consistently. The advertised resource includes its query string. The route does not trust forwarded host/protocol headers to rewrite resource identity; a proxy must preserve the URL seen by the application.

## HTTP exchange

Send the encrypted inference body (`sessionId`, `iv`, `tag`, `ciphertext`, and optional `agentId`) with `x-api-key`. An optional `idempotency-key` stabilizes challenge retries. A missing payment produces HTTP 402 with a Base64 JSON `PAYMENT-REQUIRED` header:

- `x402Version: 2` and the exact resource URL;
- `scheme: exact`, canonical `network: eip155:<chainId>`, integer token units in `amount`;
- `asset` equal to USDC and `payTo` equal to **UsageMeter**, not FeeVault;
- the token EIP-712 name/version and an opaque `extra.enclavePaymentId` identifying the request-bound intent;
- `maxTimeoutSeconds: 300` and `extra.assetTransferMethod: eip3009`.

The official client signs `TransferWithAuthorization` with a random nonce and preserves the advertised requirements. Submit the same encrypted body with the generated `PAYMENT-SIGNATURE` header. On success, HTTP 200 contains the encrypted result and receipt, and `PAYMENT-RESPONSE` contains the actual settlement transaction, payer and CAIP-2 network. All protocol headers contain standard Base64-encoded JSON.

Example using the official SDK, with an already prepared session and encrypted body:

```ts
import { x402Client, x402HTTPClient } from "@x402/core/client";
import { ExactEvmScheme } from "@x402/evm/exact/client";
import { privateKeyToAccount } from "viem/accounts";

const payer = privateKeyToAccount(payerPrivateKey);
const network = `eip155:${chainId}` as const;
const sdk = new x402HTTPClient(
  new x402Client()
    .register(network, new ExactEvmScheme(payer))
    .setSpendControls({
      allowedAssets: [{ network, asset: usdcAddress, maxAmountPerPayment: "100000" }],
    }),
);
const headers = { "content-type": "application/json", "x-api-key": apiKey };
const body = JSON.stringify(encryptedInferenceBody);
const challenge = await fetch(inferenceUrl, { method: "POST", headers, body });
if (challenge.status !== 402) throw new Error(`Expected challenge: ${challenge.status}`);
const required = sdk.getPaymentRequiredResponse(name => challenge.headers.get(name));
const payment = await sdk.createPaymentPayload(required);
const paymentHeaders = sdk.encodePaymentSignatureHeader(payment);
const response = await fetch(inferenceUrl, {
  method: "POST", headers: { ...headers, ...paymentHeaders }, body,
});
const settlement = response.headers.has("PAYMENT-RESPONSE")
  ? sdk.getPaymentSettleResponse(name => response.headers.get(name))
  : undefined;
```

SDK 2.26.0 rejects unknown/local assets by default. Explicitly allowlist the intended chain/token and set your own atomic-unit spending cap. Do not disable spend controls globally to make a local token work. Keep payer keys and payment signatures private, and never put them in URLs or logs.

If inference fails after payment, the HTTP error remains an error, but `PAYMENT-RESPONSE.success` is **true** with the proven transaction. A database finalization outage after canonical settlement also returns the proven payment with HTTP 503. Retry with the **same signed payload and body**; successful retries reuse payment and the stored result. An uncertain settlement returns `settlement_pending`; do not sign a replacement payment to work around it. The existing durable reconciler handles admitted v2 intents.

## Recovery and trust boundaries

The gateway durably binds a previously unused `(payer, nonce)` to one API-key-owned request before relaying it. The EIP-3009 signature itself authenticates payer, receiver, amount, validity window and nonce; it does **not** sign the resource, agent or provider routing. The configured meter owner remains a trusted relay for that routing.

A third party can front-run an admitted `TransferWithAuthorization` directly against the token. Recovery verifies a successful canonical direct token transaction, its exact signed calldata, and matching token-emitted `Transfer` and `AuthorizationUsed` events. The transfer must be later than the persisted canonical admission block. Recovery then invokes an owner-only meter function without charging the payer again. Both v/r/s and bytes-signature token calldata are decoded; arbitrary multicall deposits are not accepted as recovery proof.

The recovery transaction includes the funding block number/hash. The contract checks that hash atomically using `blockhash`, so a funding reorg between RPC verification and transaction execution cannot spend another deposit. Recovery requires a completed funding block within the last **256 blocks**. The API also rechecks canonical funding and settlement proofs before consuming or replaying the payment. Configured confirmations apply; deep reorgs still require the documented operator recovery procedures.

Already funded authorizations first presented to the gateway are rejected. **Do not pre-fund UsageMeter or publish a signature before gateway admission.** Public EIP-3009 signatures cannot prove which unpaid request should own a deposit. Canceled nonces, unsupported multicalls, proofs older than the blockhash window and missing/changed chain history remain quarantined for operator investigation. A used token nonce alone is never treated as proof of payment. There is no automatic refund or recovery of those unsupported deposits.

The owner-only recovery function trusts the owner to validate receipt evidence; its blockhash and signature checks do not independently verify a transaction receipt's Merkle proof. Do not expose the relay's signing key or grant arbitrary recovery calls to untrusted clients.

## Verification

`npm run test:integration` runs the SDK/HTTP/DB/chain scenarios in disposable local containers and removes them at completion. `npm run test:contracts` covers atomic settlement, mandate rollback, nonce replay, cancellation and funding-block reorg/age guards. Focused offline HTTP/protocol tests can run with:

```sh
npx vitest run --root apps/api src/x402-v2.test.ts src/x402-routes.test.ts src/x402-funding.test.ts
```
